# NPICK Core Logic

NPICK은 매주 정확히 1세트만 생성한다. 한 회차의 추천은 당첨 결과가 발표될 때까지 바뀌지 않으며, 결과가 데이터에 들어오면 해당 1세트를 평가한 뒤 다음 회차 1세트를 생성한다.

## 주간 사이클

1. `scripts/update-lotto-data.mjs`가 매주 최신 당첨번호를 가져온다.
2. 기존 pending 추천의 목표 회차가 발표됐으면 적중 번호, 적중 수, 보너스, 등수를 평가한다.
3. 최신 당첨 회차 바로 다음 회차에 대한 기록이 없을 때만 새 추천을 만든다.
4. 새 추천과 누적 평가를 `data/weekly-recommendations.js`와 JSON 파일에 저장한다.
5. 정적 앱은 생성 파일을 읽어 이번 주 1세트, 지난주 평가, 누적 결과를 표시한다.

놓친 과거 회차는 사후 생성하지 않는다. 최신 회차가 오래되어 다음 추첨일의 판매 마감 시각(한국시간 20:00)이 지났으면 데이터 갱신을 실패 처리하고 새 추천을 만들지 않는다.

## 추천 생성

`src/core/recommendation-engine.js`는 최신 당첨 회차로 결정적 seed를 만든다. 1~45를 seed 기반으로 한 번 섞은 뒤 앞의 6개로 1세트를 만든다.

- 회차당 정확히 1세트
- 세트 안에 서로 다른 번호 6개
- 같은 엔진 버전과 기준 회차는 언제 실행해도 같은 추천을 재현
- hot/cold, 최근 번호 회피, 미출현 간격, 이전 적중 피드백을 다음 번호 확률에 사용하지 않음

빈도와 미출현 통계는 화면의 참고 차트에만 사용하고 추천 번호에는 영향을 주지 않는다. 공정한 6/45에서 어떤 고정 6개 조합도 동일한 확률이므로, 검증되지 않은 과거 패턴을 다음 추천의 가중치로 사용하지 않는다.

3세트에서 1세트로 전환할 때는 이미 발표한 1234회 첫 번째 세트를 그대로 보존했다. 해당 기록의 v1 id·seed·생성 시각을 유지하고 추천 개수만 1개로 줄여 번호를 다시 뽑는 효과를 막았다. 1235회부터 새 단일세트 v2 엔진을 사용한다.

## 평가

`src/core/weekly-cycle.js`는 목표 회차가 발표되면 다음을 기록한다.

- 적중 번호와 적중 수
- 보너스 번호 포함 여부
- 등수
- 최근 52주의 평가 주차, 평균 적중 수, 3개 이상 적중 주차, 최고 적중 수

지난 결과를 다음 추천에 직접 학습시키지 않는다. 한 주의 적중이나 실패는 다음 독립 추첨의 번호별 확률을 바꾸지 않으며, 이를 즉시 가중치에 반영하면 우연을 추격하는 과적합이 되기 쉽다. 누적 결과는 추천 방식이 균등 무작위 기준보다 실제로 나은지 검증하는 용도로만 사용한다.

## 기록 무결성

각 주간 기록에는 기준/목표 회차와 날짜, 생성 시각, 판매 마감 시각, 엔진 버전, 결정적 seed, 데이터 버전, 추천 1세트가 들어간다. 평가 전 다음을 검증한다.

- `targetDraw === baseDraw + 1`
- 생성 시각이 목표 회차 판매 마감 전
- 엔진 버전과 seed가 기준 회차와 일치
- 추천 번호가 결정적 엔진 재실행 결과와 일치
- 정확히 1세트이며 세트 안의 6개 번호가 서로 다름

서비스 워커는 당첨 데이터와 주간 추천 파일에 network-first 정책을 적용해 오래된 캐시로 사후 추천이 생성되는 것을 막는다.

## 추천 성능 분석

2026-09-20부터 주간 갱신에 성능 보고서를 추가했다. 실사용 엔진은 `weekly-single-random-v2`를 유지하며, 분석은 추천 번호를 다시 뽑거나 과거 추천 기록을 만들지 않는다.

- 이론 기준: `P(H=k) = C(6,k) * C(39,6-k) / C(45,6)`. 평균 적중 수 0.8, 0개 적중 약 40.06%, 3개 이상 약 2.3834%다. 보너스는 이 세 지표의 적중 수에 포함하지 않는다.
- 실제 성적: 검증된 `evaluated` 단일 세트 기록만 포함한다. pending, invalid, 사후 재현 결과는 실제 성적에 합치지 않는다. 0개 적중 회차도 분모에 포함한다.
- 불확실성: 회차별 적중 분포를 합성해 동일한 횟수의 무작위 추천에서 나오는 평균 적중의 양측 95% 예상 범위를 구한다. 성능 추정의 신뢰구간이나 미래 보장 범위가 아니다.
- 과거 검증: 처음 260회를 준비 데이터로 두고 매번 직전 회차까지의 복사본만 전략에 전달한다. 그다음 실제 당첨번호와 비교한다.
- 구간 분리: 평가 가능한 회차 중 마지막 260회는 후반 검증 구간, 나머지는 선행 검증 구간이다. 매주 창이 이동하는 과거 분석이며 처음부터 봉인한 전향적 실험이 아니다.
- 고정 후보: 52회/260회/전체 최다 출현, 260회 최소 출현, 최장 미출현, 빈도·미출현 혼합, 홀짝·저고·합계 균형, 직전 당첨번호 제외. 동률과 샘플링 seed는 고정하며 결과를 보고 seed나 설정을 탐색하지 않는다.
- 검토 조건: 두 구간 모두 평균 적중이 0.9 이상, 0개 적중 비율이 이론값보다 5%p 이상 낮고, 3개 이상 적중 비율이 이론값 이상이어야 한다. 평균 적중의 정확한 단측 p값에 8개 후보 Bonferroni 보정을 적용해 0.05 이하여야 한다. 이 조건은 운영 검토 기준이며 미래 예측력을 입증하지 않는다.
- 기준을 통과해도 자동 채택하지 않고 추첨 전에 기록한 추가 실험을 요구한다. 결과를 보고 회차당 세트 수를 늘리지 않는다.

`npm run analyze`로 보고서를 독립 재현하며 `npm run update:data`는 당첨/추천 갱신 후 분석까지 수행한다. 보고서에는 분석 버전, 엔진 버전, 최신 회차, 정규화된 당첨 이력 SHA-256, 구간별 결과, 실제 성적을 기록한다. 앱에서 보고서 회차나 엔진 버전이 불일치하면 과거 비교를 숨기고 갱신 대기를 표시한다. 서비스 워커는 분석 파일에도 network-first 정책을 적용한다.

후보별 구체적인 규칙과 첫 검증 결과는 [recommendation-analysis.md](recommendation-analysis.md)를 참조한다.

## 확장 연구와 사전 검증

2026-09-20 재분석은 통계 32개, 학습 14개, 적응형 6개를 추가 비교한다. 입력 특성, 학습 시점, 후보 선택, 다중 비교 보정, 실용 기준은 `scripts/research/protocol.json`과 [expanded-research.md](expanded-research.md)에 고정한다. 기본 보고서의 이동 구간과 달리 선행 261~982회와 후반 983~1242회는 고정하며, 이후 실적은 사전 기록 원장으로 별도 평가한다.

- 실제 추천 엔진과 1세트 규칙은 바꾸지 않는다. 연구 모델은 앱 런타임에서 실행하지 않는다.
- 각 시점 이전 자료로만 번호별 확률·점수를 계산한다. 학습 모델은 26회마다 과거 자료만 재학습하고, 적응형 모델은 완료된 과거 예측 성적만 사용한다.
- 1243회부터 기존 방식과 후보 52개의 다음 회차 번호를 별도 원장에 고정한다. 같은 회차의 재실행, 수치 라이브러리의 플랫폼 차이, 코드 해시 변경이 기존 번호나 생성 시각을 덮어쓰지 않는다.
- 원장은 목표/기준 회차, 날짜, 생성 시각, 코드/프로토콜/입력/예측 해시를 검증한다. 당첨 결과가 발표된 기존 기록만 평가하며 지나간 회차를 채워 넣지 않는다.
- 고정 기울기의 혼합 e-process로 반복 평가의 오류를 통제한다. 최소 104회 실제 사전 평가, e값 1,040 이상, 평균 0.9개 이상, 0개 비율 약 35.06% 이하, 3개 이상 비율 약 2.3834% 이상을 모두 요구한다. 이는 검토 기준이며 달성 시점이나 성공을 보장하지 않는다.
- 기준을 통과해도 자동으로 엔진을 교체하지 않는다. 실패한 후보와 전체 결과도 함께 유지한다.

GitHub 주간 작업은 기존 앱 데이터 배포를 먼저 끝내고, 연구 테스트·계산·산출물 검증을 별도로 수행한다. 연구 실패는 작업 실패로 표시하지만 이미 완료한 주간 추천 배포를 되돌리지 않는다. 연구를 재실행할 때 기존 원장을 반드시 유지한다.

## 자동 갱신 검증

생성 데이터 테스트는 특정 회차, 특정 추천 번호, 현재 레코드의 과거 엔진 버전을 고정값으로 가정하지 않는다. 대신 최신 당첨 회차와 메타데이터의 일치, `latestDraw + 1` 목표 회차, 유효한 단일 세트, JS/JSON 산출물 동일성, 다음 회차 전환 가능성을 검증한다.

3세트에서 1세트로 바꾼 v1 기록의 보존 규칙은 생성 파일의 현재 위치에 의존하지 않는 별도 마이그레이션 fixture 테스트로 검증한다. 따라서 해당 기록이 평가 완료되거나 52주 보존 범위에서 제외되어도 정기 데이터 갱신 검증은 계속 동작해야 한다.
